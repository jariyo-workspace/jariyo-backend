# 개요

매장 운영 도메인의 조회 리팩토링을 진행했다.
`StoreQueryService`에 몰려 있던 매장/서비스/직원 소속 검증과 조회 조합 책임을 정리하고, 서비스 목록 조회 시 발생하던 per-service 직원 수 조회를 일괄 집계 방식으로 바꿨다.

# 변경 파일

- `src/main/java/com/example/jariyo_backend/domain/store/service/StoreQueryService.java`
- `src/main/java/com/example/jariyo_backend/domain/store/repository/ServiceRepository.java`
- `src/main/java/com/example/jariyo_backend/domain/store/repository/StaffServiceRepository.java`
- `src/main/java/com/example/jariyo_backend/domain/user/repository/StoreMemberRepository.java`
- `src/test/java/com/example/jariyo_backend/domain/store/service/StoreQueryServiceTests.java`

# 실행 명령

- `./gradlew test`

# 테스트 결과

- `./gradlew test` 통과

# 이슈

- 작업 시점에 `jariyo-docs` 디렉터리에 기존 변경사항이 있어 해당 변경은 건드리지 않았다.
- 이번 리팩토링은 외부 API 구조를 바꾸지 않고 조회 내부 구조와 오류 코드 일관성을 정리하는 범위로 제한했다.

# 후속 작업

- `StoreQueryService` 내부 record DTO를 별도 `dto` 패키지로 분리할지 검토
- 관리자용 매장 운영 API가 늘어날 것을 대비해 조회 전용 reader/service 계층을 더 세분화할지 검토
- 서비스/직원/정책 수정 API 구현 시 이번에 정리한 `store/service/staff` 소속 검증 규칙을 공통 재사용 구조로 확장

# 셀프리뷰

- `02-data-model.md`, `04-api-spec.md`를 다시 확인하고 매장 운영 도메인의 경계와 오류 코드 정의를 기준으로 작업했다.
- 문서상 이미 `STORE_NOT_FOUND`, `SERVICE_NOT_FOUND`, `STAFF_NOT_FOUND`가 정의돼 있어 별도 문서 수정은 하지 않았다.
- `./gradlew test`로 전체 회귀를 확인했다.
- `reports`에 작업 보고서를 추가했다.
- 조회 성능과 책임 분리는 개선됐지만, 매장 운영 도메인 전체는 아직 조회용 서비스 하나에 DTO가 많이 모여 있어 추가 분리가 필요하다.
