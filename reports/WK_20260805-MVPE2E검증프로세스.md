## 개요

MVP 대상 E2E 검증은 기존 `test`, `integrationTest` 자동 검증 위에 실제 API 호출 순서를 따라가는 수동 시나리오를 얹는 방식으로 진행한다. 목적은 구현 단위의 정상 동작 확인이 아니라, 고객과 운영자 입장에서 핵심 흐름이 끊기지 않는지 확인하는 것이다.

## 자동 검증 선행 단계

1. `./gradlew test`로 단위 테스트와 컨트롤러 테스트를 먼저 통과시킨다.
2. `./gradlew integrationTest`로 PostgreSQL 기반 통합 흐름을 통과시킨다.
3. 자동 검증이 실패하면 수동 E2E를 시작하지 않고 먼저 원인을 정리한다.

현재 자동 검증이 커버하는 주요 범위는 다음과 같다.

- 인증: 회원가입, 로그인, refresh token 재발급, 재사용 감지, 로그아웃, 내 정보 조회
- 예약: 생성, 조회, 취소, 이력, 멱등성, 목록 정렬/페이지네이션, 취소 마감, 동시성 충돌
- 예약 대기: 대기 신청, 빈자리 제안 생성, 수락, 만료, 직접 예약과의 경합
- 현장 대기: 등록, 호출, 호출 응답, 체크인, 서비스 시작/완료, 대기열 재계산, 호출 만료, 멱등성

## 수동 E2E 환경 준비

1. 로컬 PostgreSQL과 애플리케이션 기동 환경을 맞춘다.
2. 운영자 계정 1개, 고객 계정 2개, 테스트 매장 1개를 준비한다.
3. 테스트 매장에는 다음 기본 데이터가 있어야 한다.

- 활성 서비스 1개 이상
- 예약 가능 직원 1명 이상
- 영업시간
- 직원 근무시간
- 예약/현장 대기 처리 가능한 매장 멤버 권한

4. 테스트 데이터는 가능하면 고정 ID 또는 명확한 이메일 규칙으로 재생성 가능하게 관리한다.

## 수동 E2E 실행 순서

### 1. 고객 인증 흐름

- 회원가입 또는 기존 고객 로그인
- `GET /api/v1/me` 조회
- access token 만료 또는 refresh 시나리오가 필요하면 별도 세션에서 확인

기대 결과:

- 고객 토큰으로 `me` 조회가 성공해야 한다.
- 마스킹된 개인 정보와 역할 정보가 일관되게 반환되어야 한다.

### 2. 예약 진입 흐름

- `GET /api/v1/stores`
- `GET /api/v1/stores/{storeId}`
- `GET /api/v1/stores/{storeId}/services`
- `GET /api/v1/stores/{storeId}/services/{serviceId}/staff`
- `GET /api/v1/stores/{storeId}/availability`

기대 결과:

- 프론트가 예약 화면을 그리는 데 필요한 매장, 서비스, 직원, 슬롯 정보가 모두 연결된다.

### 3. 예약 핵심 흐름

- `POST /api/v1/reservations`
- `GET /api/v1/me/reservations`
- `GET /api/v1/reservations/{reservationId}`
- `GET /api/v1/reservations/{reservationId}/history`
- `POST /api/v1/reservations/{reservationId}/cancel`

검증 포인트:

- 같은 `Idempotency-Key` 재전송 시 동일 결과 재반환
- 다른 요청 본문으로 같은 키 재사용 시 오류 반환
- 취소 후 상태 이력 반영

### 4. 예약 대기 흐름

- 예약이 없는 슬롯이 아니라 이미 점유되거나 막힌 시간대로 조건을 잡는다.
- `POST /api/v1/waitlists`
- `GET /api/v1/me/waitlists`
- `GET /api/v1/waitlists/{waitlistId}`
- 예약 취소를 유도해 빈자리 제안 생성
- `GET /api/v1/me/slot-offers`
- `GET /api/v1/slot-offers/{offerId}`
- `POST /api/v1/slot-offers/{offerId}/accept`

검증 포인트:

- 수락 후 예약이 실제로 생성되는지 확인
- 대기 상태가 `RESERVED`로 전이되는지 확인
- 동일 빈자리를 직접 예약과 동시에 가져가지 못하는지 확인

### 5. 현장 대기 흐름

- `GET /api/v1/stores/{storeId}/walk-in-status`
- `POST /api/v1/walk-ins`
- `GET /api/v1/me/walk-ins`
- `GET /api/v1/walk-ins/{walkInId}`

검증 포인트:

- 대기 등록 후 `waitingAhead`, 예상 대기 시간, 상태가 일관되게 계산되는지 확인
- 같은 고객의 중복 활성 현장 대기가 차단되는지 확인

### 6. 운영자 처리 흐름

- 운영자 로그인
- `GET /api/v1/admin/stores/{storeId}/dashboard/today`
- `GET /api/v1/admin/stores/{storeId}/reservations`
- `GET /api/v1/admin/stores/{storeId}/waitlists`
- `GET /api/v1/admin/stores/{storeId}/walk-ins`
- 예약 고객: 체크인, 노쇼 처리, 서비스 시작, 서비스 완료
- 현장 고객: 호출, 재호출 필요 시 호출, 체크인, 서비스 시작, 서비스 완료

검증 포인트:

- 매장 소속이 아닌 운영자는 접근이 막혀야 한다.
- 잘못된 상태 전이는 서버가 차단해야 한다.
- 완료된 서비스 세션과 상태 이력이 운영 화면에 반영되어야 한다.

## 실패 경로 검증 우선순위

실패 경로는 성공 경로를 모두 통과한 다음 별도 세션에서 수행한다.

1. 권한 오류
2. `Idempotency-Key` 재사용 오류
3. 중복 예약 또는 동일 슬롯 경합
4. 취소 마감 초과
5. 만료된 호출 응답 또는 이미 종료된 대기 처리
6. 이미 완료된 서비스에 대한 재처리

## 결과 기록 방식

각 시나리오는 아래 형식으로 기록한다.

- 시나리오명
- 선행 데이터
- 요청 순서
- 기대 결과
- 실제 결과
- 발견 이슈
- 재현 여부

발견 이슈는 바로 별도 GitHub issue로 분리하고, 원래 E2E 검증 이슈에는 링크만 남긴다.

## 권장 운영 방식

- 1차: 수동 E2E로 정상/실패 흐름 검증
- 2차: 반복되는 성공 경로를 API 컬렉션으로 고정
- 3차: 안정화된 핵심 흐름만 `integrationTest` 또는 별도 E2E 자동화로 승격

이 순서를 지키는 이유는, 아직 운영 데이터 준비와 상태 전이 관찰이 중요한 단계에서 자동화부터 밀어붙이면 시나리오보다 픽스처 유지 비용이 더 커지기 때문이다.
